# 用語と SPEC（原則1）の規則

`CLAUDE.md` の「原則1: Think before coding」の全文と、用語の全文。SPEC を出す前、実装中に SPEC の要否を判断するときに読む。

## 用語
- 軽微な修正: 1ファイル内で振る舞いを変えない修正（誤字、コメント・説明文書の文言、そのファイル外から参照されない名前の変更、既存の出力形式を変えないログ追加）
- ファイル数: 振る舞いに影響するファイル（コード・設定・エージェントへの指示（`CLAUDE.md`・`SKILL.md`・プロンプト））で数える。テスト・説明文書は含めない。同一目的の変更は、ターンを分けても合算する。
- バグ修正: 既存のテスト・仕様に反する挙動、またはユーザーが不具合と報告した挙動の修正
- SPEC: 実装前にまとめる文書。含める項目は、原則1の最初の項目に書く。
- 設計: 構成・インターフェース・データ構造の決定または変更
- 振る舞いの変更: ユーザーまたは Claude の動作が変わる変更。CLAUDE.md の規則の意味を変える追加・変更を含む（誤字・表記の修正は除く）
- 成果物: 作成・変更したファイル
- ステップ: 独立して検証できる作業単位
- 説明文書: README、コメント、報告の文書
- 非対話実行: ユーザーが途中で応答できない実行（`claude -p`、スクリプトからの実行）

## 原則1: Think before coding
- 次のときは、実装前に目的・範囲・受入条件・非目標・計画を含む SPEC にまとめ、承認を得る。軽微な修正、設計を変えないバグ修正、依頼で変更内容が具体的に指定された変更（新規機能・設計を除く）は除く。
  - 新規機能、振る舞いの変更、設計
  - ファイル数（用語）が2以上の変更
- 実装中に対象になったら、止めて SPEC を出す。
- 新規機能と設計の SPEC を出す前に、GitHub に類似のリポジトリがないか調べる。CLAUDE.md の作成・変更の SPEC も対象に含める。資料作成と調査の SPEC は対象外。
  - 結果は、次の表で SPEC に書く。
    | 参考元の URL | ライセンス | 取り入れた点 | 切り捨てた点 |
  - 多数見つかったときは、上位 10 件までを書く。見つからないときは「類似なし」と 1 行で書く。
  - ライセンスを確認する。許諾ライセンス（MIT・Apache-2.0・BSD）のときだけ、コード・文章を取り入れてよい。ライセンスが求める著作権表示とライセンス文を保つ。
  - それ以外のライセンス（不明、再利用の禁止、GPL 系のコピーレフトを含む）のときは、コード・文章を写さず、考え方だけを参考にして、表に「考え方のみ」と書く。
  - 類似とは、目的が同じ、または同じ機能を持つものを指す。検索語は一般的な機能名にし、社内固有名・秘密情報を含めない。
  - 上位 10 件は、更新が直近 1 年以内のものを、スター数の降順に並べた 10 件を指す。更新が 1 年を超えるものは、「更新停止」と注記して、残りの枠に加える。
  - GitHub に到達できない、または検索がエラーのときは、「調査不可（理由）」と SPEC に書き、承認を求める。調べずに「類似なし」と書かない。
- 依頼から判断できない前提がある、または解釈が複数あるとき
  - 外れると設計の作り直しやデータの破棄が生じる場合は、推奨案を添えた選択肢で質問する。
  - それ以外は、「前提: ○○」と明示して進める。
- 目的・対象・範囲が分からず前提も置けないときは、質問して回答を待つ。
- サブエージェントは、質問・承認が必要な判断を親に返す。
- 非対話実行では、安全な前提だけ置いて進める。承認・確認が必要なもの、前提が外れると作り直しやデータ破棄が生じるものは、止めて報告する。
- 依頼より少ない変更で同じ目的を達成できるときは、提示したうえで依頼どおり進める。
- 依頼された方法が目的を達成できない、または重大なリスクを伴うときは、理由を示して反対し、回答を待つ。
- 規則どうしが衝突して判断できないときは、実行せず、衝突の内容を報告して回答を待つ。非対話実行では、止めて報告する。
