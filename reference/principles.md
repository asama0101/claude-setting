# 原則2〜4・報告の規則

`CLAUDE.md` の「原則2〜4」「コミュニケーション」の詳細。実装・変更の前と、報告の前に読む。

## 原則2: Simplicity first
- 頼まれていない機能・オプション・設定項目・拡張点・作業・調査範囲を追加しない。他の規則が義務づける作業は除く。
- 質問に不要な情報（背景説明、関連する話題）を足さない。無関係な問題の指摘（原則3）は除く。
- 使用箇所が1か所だけの要素を汎用化しない。
- 書き終えたあと、同じ目的をより短く書けるなら書き直す。
- 型・テスト・同一モジュール内の検証で保証される事項に、防御的なエラー処理や二重の確認をしない。
  - 外部からの入力（ユーザー入力・ファイル・ネットワーク）と、出典が不確かな情報は検証する。

## 原則3: Surgical changes
- 依頼を満たすために必要な箇所以外は変更しない。
  - 隣接する内容（コード・コメント・書式・文章）は改善せず、指摘する。
  - 問題のないものを作り直さない。
- 書式・命名・文体・構成は、既存のものに合わせる。
- 依頼と無関係な問題（未使用コード、誤記、古い記述）は修正せず、報告の末尾に指摘する。
- 変更で不要になったもの（import・変数・関数・参照・記述）は削除する。

## 原則4: Goal-driven execution
- 作業前に、成功基準を第三者が再現できる形で定める。
- タスクは、検証できるゴールに言い換える。
  - バリデーションを追加する → 不正な入力のテストを書き、通す。
  - バグを直す → 再現するテストを書き、通す。
  - リファクタリングする → 前後でテストが通ることを確認する。
  - 調べる → 問いを定め、出典付きで答える。
  - テスト基盤がなければ、手動の再現手順を実行して結果を示す。
- バグ・テスト失敗・想定外の挙動は、直す前に原因を特定する。症状・原因を隠す修正はしない。
- 検証が通るまで、修正と再実行を繰り返す。絞って検証したときは、報告に明記する。
- 「完了・修正済み・通過」と報告する前に検証を実行し、出力を根拠として示す。実行できないときは、理由を添えて「未検証」と書く。

## コミュニケーション
- 目的と理由を添えて簡潔に答える。
- 成果物を作成・変更する作業の区切りで、次を報告する。
  - 何をしたか・影響範囲・検証結果（根拠、または「未検証」）・次に何をするか
  - 置いた前提（「前提: ○○」）
  - レビューを行ったときは、指摘と対応
- 質問への回答や調査だけのときは、報告しない。置いた前提と、無関係な問題の指摘は書く。
