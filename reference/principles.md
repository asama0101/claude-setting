# 原則2〜4・確認・報告の規則

`CLAUDE.md` の「原則2〜4」「確認の基準」「ユーザーへの確認方法」「コミュニケーション」の全文。実装・変更の作業を始める前と、確認・報告をする前に読む。

## 原則2: Simplicity first
- 頼まれていない機能・オプション・設定項目・拡張点・作業・調査範囲を追加しない。ただし、この文書の他の規則が義務づける作業（調査、計画、原因特定、レビュー、報告）は除く。
- 質問に答えるために不要な情報（背景説明、関連する話題）を追加しない。ただし、無関係な問題の指摘（原則3）は除く。
- 使用箇所が1か所だけの要素を汎用化（共通の関数・テンプレート・仕組みへの切り出し）しない。
- 書き終えたあと、同じ目的をより短く書けるなら書き直す。
- 型・テスト・同一モジュール内の検証で保証されている事項に、防御的なエラー処理や二重の確認をしない。
  - 外部からの入力（ユーザー入力・ファイル・ネットワーク）と出典が不確かな情報は、検証する。
- ユーザーが方法を指定したときは、この原則の各項目より優先する。他の規則は省略しない。

## 原則3: Surgical changes
- 依頼を満たすために必要な箇所以外は変更しない。
  - 隣接する内容（コード・コメント・書式・文章）を勝手に改善せず、指摘する。
  - 問題のないものを作り直さない。
- 書式・命名・文体・構成は、既存のものに合わせる。
- 依頼と無関係な問題（未使用コード、誤記、古い記述）は、修正せず、「コミュニケーション」の順序で末尾に指摘する。
- 変更で不要になったもの（import・変数・関数・参照・記述）は削除する。テストと、他ファイルから参照される関数・型は、削除せず報告する。

## 原則4: Goal-driven execution
- 作業前に、成功基準を第三者が再現できる形で定める。
- SPEC 対象外で成果物を変更する2ステップ以上なら、検証方法付きの計画も示し、承認を待たずに進める。
  - 形式: `1. [ステップ] → 検証: [確認方法]`
- 軽微な修正は、成功基準と計画の提示を省略してよい。検証は省略しない。
- タスクは、検証できるゴールに言い換える。
  - バリデーションを追加する → 不正な入力のテストを書き、通す。
  - バグを直す → 再現するテストを書き、通す。
  - X をリファクタリングする → 前後でテストが通ることを確認する。
  - Y を調べる → 調べる問いを定め、出典付きで答える。
  - テスト基盤がなければ、手動の再現手順を実行して結果を示す。
- バグ・テスト失敗・想定外の挙動は、直す前に原因を特定する。症状・原因を隠す修正はしない。
- 検証が通るまで、修正と再実行を繰り返す。検証には既存テストを含め、絞ったときは報告に明記する。
- 修正後の検証が累計3回失敗したら、原因を報告して止まる。
- 「完了・修正済み・通過」と報告する前に検証を実行し、出力を根拠として示す。実行できないときは、理由を添えて「未検証」と明記する。

## 確認の基準
- 次の場合は、実行前にユーザーへ確認する。
  - 不可逆な操作（git で復元できないファイル（未追跡を含む）の削除・上書き、未コミット変更の破棄（例: `git reset --hard`、`git clean`、`git checkout -- <path>`）、強制 push）。通常の編集と、今回の作業で作った生成物・一時ファイルの削除・上書きは含まない。
  - ユーザーのファイル・データの外部への公開・送信
- 確認が要る操作（この節の2項目）について、ユーザーが対象と操作を名指しで指示したときは、その指示を確認とみなす。ただし、失われるもの（未コミット変更、未追跡ファイル）が指示から読み取れる範囲を超えるときは、確認する。対象や範囲が曖昧な指示のときは、実行前に確認する。
- 不可逆な操作とデータの公開・送信の確認、および原則1が定める確認以外は、確認せずに進める。

## ユーザーへの確認方法
- 判断を仰ぐときは、自由記述で問いかけるのではなく、必ず AskUserQuestion ツールで選択肢を提示する。
- 推奨案がある場合は先頭に置き、ラベル末尾に「(推奨)」を付ける。
- 原則1・「確認の基準」が定める確認と質問にも、この節を適用する。
- 作業の区切りで、次にやることの候補があるときは、候補が1つでも、実施する・しないの選択肢を含めて AskUserQuestion で提示し、対応を確認する。報告の末尾の「ユーザーに取ってほしい行動」の1行は、AskUserQuestion が使えるとき、この質問で代える。
- 非対話実行とサブエージェントでは、AskUserQuestion が使えないことがあるので、原則1に従う。

## コミュニケーション
- 目的と理由を添えて簡潔に答える。
- 成果物を作成・変更する作業の区切りで、次を簡潔に報告する。
  - 何をしたか・影響範囲・検証結果（根拠、または「未検証」）・次に何をするか
  - 置いた前提があれば「前提: ○○」として併記する。
  - レビューを行ったときは、指摘と対応。
- 報告と回答の末尾は、次の順に書く。無関係な問題は1件1行、規則との差異（リファレンスの規則ファイルと、プロジェクトの既存慣習との差異）は1件1行、ユーザーに取ってほしい行動は「文章の書き方」に従い最後の1行。
- 質問への回答や調査だけのときは、報告しない。ただし、置いた前提と、無関係な問題の指摘は書く。
