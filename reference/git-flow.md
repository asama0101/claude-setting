# Git/GitHub の基本フロー

Hook（`hooks/git_flow.py`）が守らせる GitHub Flow の規則。Git 管理外のフォルダでは、Hook は何もしない。

## 基本フロー

1. 作業ブランチを切る
   - main の最新を取り込む。
2. 編集する
   - ファイルを作成・削除・編集する。
3. コミットする
   - Conventional Commits の形式にする（type は英語、説明は日本語）。
   - 例: `docs: git-flow.md の段階7を直す`
4. push する
   - 作業ブランチを origin に push する。
5. PR を作る
   - タイトルも Conventional Commits の形式にする。
6. レビューを受ける
7. マージする（ユーザー）
   - ユーザーが `--squash` で main にマージする（1 PR = 1 コミット）。
   - Claude はマージしない。
   - Claude は、PR の URL と `gh pr merge <番号> --squash` を案内する。
8. 作業ブランチを削除する
   - 契機: ユーザーがマージしたと伝えたとき、または Hook が作業ブランチの PR のマージ済みを知らせたとき。
   - Claude が削除する。手順は「作業ブランチを削除するとき」。
9. リリースする
   - 契機: 段階8のあと、またはセッション開始時に「リリース未作成」の案内を見たとき。
   - 提案する版を決める。`skip` のときは、聞かずに終わる。
   - Claude が AskUserQuestion で「リリースする／しない」を聞く。
   - リリースする場合は、タグ（`vMAJOR.MINOR.PATCH`）を打ち、GitHub Release を作る。

## ブランチ名

`<type>/<短い名前>` の形にする。type は次の4つ。

- `feat/`: 機能の追加
- `fix/`: 不具合の修正
- `docs/`: 文書だけの変更
- `chore/`: 設定・保守の変更

## バージョン表記の定義

バージョンはタグだけで持つ。VERSION ファイルは置かない。

| 項目 | 定義 |
|---|---|
| 書式 | `v` + `MAJOR.MINOR.PATCH`。先頭に0を付けない。例: `v1.2.3`。 |
| プレリリース | 作らない。 |
| 最初の版 | タグがなければ `v0.1.0` を提案する。 |
| 版を決める材料 | 前のタグから既定ブランチまでのコミット件名。最大の種類で決める。type のないコミットは数えない。 |
| `feat` | MINOR を上げ、PATCH を0にする。 |
| `fix`・`perf`・`refactor` | PATCH を上げる。 |
| `docs`・`chore`・`test`・`ci`・`style`・`build` だけ | 版を上げない。`skip` を提案し、リリースを作らない。 |
| 破壊的変更（`!` または `BREAKING CHANGE:`） | 1.0.0 以上では MAJOR を上げ、他を0にする。 |
| 0.y.z の間 | 破壊的変更も MINOR を上げる。1.0.0 にするのは、ユーザーが明示したときだけ。 |
| 検査 | `git tag` のタグ名が、下の正規表現に合わなければ拒否する。 |

```text
^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$
```

## 各段階を Hook がどう扱うか

「既定ブランチ」は、`origin/HEAD` が指すブランチ。なければ `main`、`master` の順。
PR の工程（段階4の push 待ち、5）と、段階8・9の案内は、`origin` が `github.com` のときだけ動く。

| 段階 | 扱い | 内容 |
|---|---|---|
| 1 ブランチを切る | 強制（deny）＋確認 | 既定ブランチ上の編集・削除・commit・merge・push を拒否する。「切らない」を選んだセッションは外れる。 |
| 2 編集 | 記録 | 編集の記録を残す。 |
| 3 コミット | 促し（block） | 編集したセッションだけ、コミットを促す。メッセージの形式は検査しない。 |
| 4 push | 促し（block）＋強制（deny） | 編集したセッションだけ、push を促す。force push と既定ブランチへの push は拒否する。 |
| 5 PR 作成 | 促し（block） | 編集したセッションだけ、PR 作成を促す。タイトルの形式は検査しない。 |
| 6 レビュー | 助言のみ | Hook では扱わない。 |
| 7 マージ | 強制（deny） | `gh pr merge` を、どこで実行しても拒否する（`-R` 付きも）。マージはユーザーが行う。`gh api`、`bash -c` 経由は拒否できない。Hook は誤操作を防ぐ層である。 |
| 8 作業ブランチの削除 | 促し（block） | 作業ブランチの PR がマージ済みで、ローカルの先頭が PR の先頭と一致するとき、セッション開始時に知らせ、応答の終了時に促す（編集がなくても）。同じ状態では1回だけ促す。削除の操作は検査しない。 |
| 9 タグとリリース | 強制（deny）＋助言 | 新しいタグ名が書式に合わなければ拒否する。セッション開始時に、未リリースのコミットがあり、提案する版が `skip` でなければ、提案する版を知らせる。 |

## ブランチを切らないとき

「切らない」を選ぶと、Claude が `git_flow.py allow-main <セッション ID>` を実行する。そのセッションの間だけ、ブランチ確認と、既定ブランチへの commit・push の拒否が外れる。
force push は外れない。

## 作業ブランチを削除するとき

マージ済みと分かったときに行う。squash マージでは、作業ブランチのコミットが既定ブランチに入らない。そのため `git branch -d` の判定は当てにならない。`-D` を使い、その代わりに、削除の前に次の確認をする。

1. 次を確認する。どれかが満たされなければ、止めてユーザーに報告する。
   - `gh pr view <作業ブランチ> --json state,headRefOid` の state が MERGED である。
   - `headRefOid` が `git rev-parse <作業ブランチ>` と一致する（PR のあとにローカルで足したコミットを消さないため）。
   - `git status` で、未コミットの変更がない。
   - `gh pr list --base <作業ブランチ> --state open` が空である（積み重ねた PR を、origin の削除で閉じないため）。
   - `headRefOid` が一致しないときは、`git fetch origin` を行う。`origin/<作業ブランチ>` が `headRefOid` と一致し、ローカルの先頭がその祖先であれば、一致したものとみなす（Web 側で PR が進んだ場合）。みなせないときは、削除せずに報告する。
2. `git switch <既定ブランチ>` と `git pull --ff-only` で、最新を取り込む。
3. `git branch -D <作業ブランチ>` を実行する。
4. origin の作業ブランチが残っていれば、`git push origin --delete <作業ブランチ>` を実行する（GitHub の自動削除で消えているときは省く。`git fetch --prune` で確かめる）。

2〜4が失敗したとき（`git worktree` で別のフォルダが使用中のときなど）は、止めてユーザーに報告する。

## リリースするとき

段階8のあと、またはセッション開始時に「リリース未作成」の案内を見たときに行う。

1. 提案する版を決める。前のタグから `origin/<既定ブランチ>` までのコミット件名と、「バージョン表記の定義」から決める。`skip` のときは、聞かずに終わる。
2. AskUserQuestion でユーザーに「リリースする（提案する版）／しない」を聞く（版の確認と兼ねる）。
3. リリースする場合は、次を実行する。
   - `git fetch origin`
   - `git tag <版> origin/<既定ブランチ>`
   - `git push origin <版>`
   - `gh release create <版> --generate-notes`
