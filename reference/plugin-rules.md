# スキル・プラグイン作成の共通ルール

Claude Code のスキル・プラグインを新規に作る・変更するときに従う規則。

- 規則には **必須** と **推奨** がある。必須は守る。推奨は、守らない理由があれば外してよい（理由は README に残す）。
- 必須・推奨は、この文書の社内基準である。公式ドキュメントの必須とは限らない。公式の仕様に依存する規則には〔公式〕を付ける（仕様が変わったら、これらを先に見直す）。
- 各規則は「規則」と「理由」で書く。例外のときは理由で判断する。
- Python の専用環境の規則（A1・A4・A5・A6・A7・H5 の Python の部分）は、`~\.claude\rules\python-venv.md` の 2 に書く。`.py` を扱うと自動で読み込まれる。この文書には、言語を問わない部分を書く。
- `<PLUGIN>` はプラグイン名、`<SKILL>` はスキル名、`<名前>` は各自が決める名前を表す。
- Windows 前提で書く。他の OS は確認していない（専用環境の Python のパスが `bin/python` になるなど、違いがある）。
- グローバルの CLAUDE.md にある規則（確認の基準・完了前の検証）はここに重ねて書かない。そちらに従う。チェックリスト（G）にも載せない。
- 公式ドキュメントの記載は 2026-10-23 時点で確認した。

## 用語

- **プラグイン**: `.claude-plugin/plugin.json` を持つ配布単位。スキル・agent などを含む。
- **単体スキル**: プラグインに属さないスキル（`~/.claude/skills/<名前>/`、またはプロジェクトの `.claude/skills/`）。
- **専用環境**: プラグイン（単体スキル）だけが使う実行環境。Python の専用環境は `python-venv.md` の 2 に従う。
- **置き場**: 専用環境と状態（設定・キャッシュ）を置くディレクトリ。プラグインでは `${CLAUDE_PLUGIN_DATA}`。
- **入口スクリプト**: SKILL.md が最初に呼ぶスクリプト。専用環境の Python を探して本体を実行する。標準ライブラリだけで動かす。サブコマンド `doctor`・`setup` を持つ（A6）。
- **副作用**: ファイルの書き込み、外部への送信、常駐。
- **README**: この文書で単に「README」と書いたものは、リポジトリ直下の `README.md` を指す。README は直下に 1 つだけ置き、プラグインのフォルダの中には置かない（readme-rules.md の 4）。

## A. 実行環境と状態の置き場

### A1. 専用環境だけで実行する（必須）

- **規則**: 本体は専用環境の中だけで実行する。システム側の実行環境（Python なら `python-venv.md` の 2-1）は入口スクリプトの起動にだけ使い、ライブラリは入れない・読まない。
- **理由**: 利用者のシステムに何が入っているかで動作が変わらないようにするため。システムの環境と専用環境の「どちらかを選ぶ」分岐は、動作の再現を難しくするので作らない。
- 原則は言語を問わない。Python の具体的な手順は `python-venv.md` の 2-1 に書く。Node など他の言語は、同じ原則（専用の置き場・版の固定・承認後の導入）を当てはめる。
- Node の中で Python の venv を作るような混成構成も、置き場は A2、承認は A5、固定は A4 に従う。

### A2. 置き場は `${CLAUDE_PLUGIN_DATA}`（必須）〔公式〕

- **規則**: 専用環境と状態は `${CLAUDE_PLUGIN_DATA}` に置く。`${CLAUDE_PLUGIN_ROOT}` には状態を置かない。
- **理由**: `${CLAUDE_PLUGIN_ROOT}` は更新でパスが変わり中身が入れ替わるキャッシュ領域で、置いたものが消える。`${CLAUDE_PLUGIN_DATA}` は更新後も残る。
- 参考（公式の事実）:
  - 解決先は `~/.claude/plugins/data/<id>/`。`<id>` は、プラグイン識別子の英数字・`_`・`-` 以外を `-` に置き換えたもの（例: `my-plugin@my-marketplace` → `my-plugin-my-marketplace`）。
  - 最後のインストール先からアンインストールすると、既定では消える（`--keep-data` で残せる）。
  - 環境変数 `CLAUDE_CODE_PLUGIN_CACHE_DIR` を設定すると、プラグインの置き場全体が変わる。
  - Windows の実パスは公式に記載がない。実機（pptx-deck）で `C:\Users\<ユーザー>\.claude\plugins\data\<id>\` を確認した。
- `claude --plugin-dir` で読み込むと、`<id>` は `<名前>-inline` になり、本番と別の置き場になる。開発時は A7 の `<PLUGIN>_HOME` で置き場を固定する。
- プラグインごとに `<id>` が別なので、プラグイン間で環境を共有しない。

### A3. 変数は引数で渡す（必須）〔公式〕

- **規則**: `${CLAUDE_PLUGIN_ROOT}`・`${CLAUDE_PLUGIN_DATA}` は、SKILL.md（と agent）の本文に書く。入口スクリプトには、引数で渡す。入口スクリプトが環境変数から読むことを前提にしない。

      python "${CLAUDE_PLUGIN_ROOT}/<入口スクリプト>" --data "${CLAUDE_PLUGIN_DATA}" <サブコマンド>

- **理由**: これらの変数は、Bash ツールで実行するコマンドの環境変数には入らない（メインセッションもサブエージェントも）。Claude Code が展開するのは、スキル・コマンド・agent の本文のほか、hooks、monitor、MCP、LSP の設定の中である（公式の manifest reference の表）。（hooks・MCP の stdio・LSP では、環境変数としても渡る。）`allowed-tools` の中での `${CLAUDE_PLUGIN_ROOT}` の展開は、公式ページに明記がない（`${CLAUDE_SKILL_DIR}` は明記あり）。pptx-deck・pj-lens はこの形を使っているので、変えるときは実機で確かめる。
- Windows では、展開後のパスの区切りがスラッシュになる。例のコマンドは Bash 構文である。
- 引数（`--data`）と環境変数（`<PLUGIN>_HOME`）の境界: SKILL.md → 入口スクリプトは引数。入口スクリプト → 子プロセスは環境変数（A7）。

### A4. 依存は `==` で固定する（必須）

- **規則**: 依存は固定用のファイルで管理し、すべて版を固定する（Python は `python-venv.md` の 2-2、Node は `package-lock.json`）。固定する版は、新しい専用環境で全テストが通った版にする。
- **理由**: 環境を作るたびに同じものが入り、動作を再現できるようにするため。
- 環境の版が固定用のファイルとずれたら、入口スクリプトが検知して終了コード 3 で止める（A6）。再同期は自動にせず、承認後の `setup --yes` で行う。

### A5. 導入は利用者の承認を得てから（必須）

- **規則**: 環境（言語の専用環境・ブラウザなど、容量が大きいもの）の導入は、利用者に「どこに・何を・どのくらいの容量で入れるか」を説明して承認を得てから行う。承認なしには作らない。
- **理由**: 利用者の環境を、承認なしに変えないため。
- 環境が機能の前提のとき: `setup`（`--yes` なし）は、作成先と内容を表示して終了コード 3 で止まる。承認後に `setup --yes` で作る。
- 小さな任意依存（なくても本体は動き、その機能だけ使えない）のとき: 承認を得て導入するか、代替手段を案内して止まる。承認なしに導入しない。`setup` の流れまでは求めない。
- 動かなくなった環境を作り直すのは、承認済みの場所だけにする。Python の場合は `python-venv.md` の 2-3。

### A6. 入口スクリプトの契約（必須）

- **規則**: 入口スクリプトは、サブコマンド `doctor`（診断のみ。何も変更しない）と `setup`（A5）を持ち、終了コードを次のとおりにする。
  - 0: 成功
  - 1: 実行時のエラー
  - 2: 引数・設定のエラー（置き場が決まらない、など）
  - 3: 専用環境が使えない（未作成・版のずれ・壊れている・承認待ち）
- 終了コード 3 のとき、不足の内容と `setup` の案内を出す。案内には、環境の置き場を含める。Python の場合の追加の規則は `python-venv.md` の 2-4。
- **理由**: どのプラグインでも同じ振る舞いにすると、SKILL.md が「終了コード 3 のときは、利用者に確認して `setup --yes` を実行する」と書ける。設定エラーを別コード（2）にして、誤って環境を作らないようにする。
- 専用環境を使わない（標準ライブラリだけで動き、導入するものがない）スクリプトには、`doctor`・`setup`・終了コード 3 を求めない。環境を使うスクリプトが複数のうちの一部だけ（Node のプラグインが、Excel の読み取りだけ Python の venv を使う、など）のときは、環境を使うスクリプトだけが `doctor`・`setup`・終了コード 3 を持てばよい。

### A7. 置き場の上書きと優先順（推奨）

- **規則**: テストや特殊な環境のために、置き場を上書きする環境変数 `<PLUGIN>_HOME` を用意する。置き場の優先順は次のとおり。
  1. 環境変数 `<PLUGIN>_HOME`
  2. 引数 `--data <パス>`（SKILL.md が渡す `${CLAUDE_PLUGIN_DATA}`）
  3. どちらもなければエラー（終了コード 2）。`setup` の案内と `--data` の付け方を表示する。
- **理由**: 開発時もテストも、通常と同じ経路（入口スクリプト → 専用環境）で実行できる。開発専用の探索（リポジトリ内の環境の自動検出など）は作らない。Python の場合は `python-venv.md` の 2-5。
- 入口スクリプトは、`--data` を引数の先頭で取り除き、子プロセスの環境変数 `<PLUGIN>_HOME` に入れて渡す。

### A8. ブラウザなど巨大な共有バイナリは専用環境の対象外（推奨）

- **規則**: Playwright の chromium のように、他のツールと共有でき、巨大なもの（目安 100 MB 以上）は、専用環境に入れず、そのツールの既定の共有の場所に置く（Playwright は `%LOCALAPPDATA%\ms-playwright`、`PLAYWRIGHT_BROWSERS_PATH` で変更できる）。README に「共有で、専用環境の対象外」と書く。
- **理由**: 他のプラグインや利用者自身の Playwright と共有でき、重複が出ない。プラグインをアンインストールしても残る。

### A9. 単体スキルの場合（必須）〔公式〕

- **規則**: 単体スキルは、`${CLAUDE_PLUGIN_ROOT}`・`${CLAUDE_PLUGIN_DATA}` が使えない（公式に「プラグインのスキルでのみ置換」と明記）。スキルのディレクトリは `${CLAUDE_SKILL_DIR}` で指す。置き場は、次の優先順にする。
  1. 環境変数 `<SKILL>_HOME`
  2. `%LOCALAPPDATA%\<スキル名>\`（スクリプトが自分で決める）
- **理由**: 単体スキルには、更新で消えない保存先を提供する公式の仕組みがない（確認できなかった）。スキルのディレクトリの中は、利用者が編集・同期・再配置する場所で、環境や状態には向かない。`%LOCALAPPDATA%\<名前>\` は実績のある場所。
- 他の規則の適用:

  | 規則 | 単体スキル |
  |---|---|
  | A1・A4・A5・A6・A8 | そのまま適用 |
  | A2 | 置き場が上の優先順に置き換わる |
  | A3 | 適用しない（変数の代わりに `${CLAUDE_SKILL_DIR}` を使い、置き場はスクリプトが決める） |
  | A7 | 上の優先順で代替 |

- プラグインに包めるなら、A2 に従う。

## B. 本体と利用者の成果物の分離

### B1. プラグイン本体は読み取り専用（必須）

- **規則**: プラグインのディレクトリ（`${CLAUDE_PLUGIN_ROOT}`）には、実行時に何も書かない。成果物は利用者の作業側（実行ディレクトリ側）、状態は `${CLAUDE_PLUGIN_DATA}` に置く。
- **理由**: 更新でパスが変わり、中身が入れ替わるため。成果物が更新で消えたり、利用者のプロジェクトが汚れたりしない。

### B2. 作業フォルダへ写したものは、本体の更新で自動では変わらない（推奨）

- **規則**: 本体のファイルを利用者の作業側へコピーする設計にするときは、更新を届ける手段（再初期化のコマンドなど）を決めて README に書く。派生ファイルは再生成できるものだけを消し、元データは消さない。
- **理由**: コピー済みのものには、プラグインを更新しても修正が届かない。
- 実例: pptx-deck の `init --force`・`reopen` と派生ファイルの一覧。

## C. SKILL.md / agent の書き方

### C1. frontmatter と description（必須）〔公式〕

- **規則**: frontmatter には `name` と `description` を書く。`name` はディレクトリ名と一致させる。description には、次の 3 点を書く。
  1. 何をするか
  2. 使う場面（利用者の言い回し）
  3. 使わない場面と、代わりに使うスキル（`disable-model-invocation: true` のスキルは省略可）
- **理由**: `name` の一致は、F1 で機械検査できるようにするため（公式では既定値で、必須ではない）。description の 1・2 は、起動のしやすさのため。3 は、似たスキルへの誤った起動を防ぐため。description は `when_to_use` と合わせて 1,536 文字で切られる（公式）ので、長く書きすぎない。
- OS・Python の版・MCP の要否などは、任意項目 `compatibility` に書いてよい（pptx-deck の運用）。

### C2. パスの書き方（必須）

- **規則**: プラグイン内の SKILL.md と agent のコマンドは、`${CLAUDE_PLUGIN_ROOT}/…` を基準に書く。ハードコードした絶対パス（`C:/Users/…`）、`${CLAUDE_SKILL_DIR}`、相対リンク、地の文の相対パスを書かない。単体スキルは A9 に従う。
- **理由**: インストール先はキャッシュで、更新でパスが変わる。相対パスは、実行時の作業ディレクトリで意味が変わる。基準を 1 つにそろえて機械検査できるようにするため、`${CLAUDE_SKILL_DIR}` は禁止する（公式は制限していない。`${CLAUDE_SKILL_DIR}/../..` のように、スキルの外を指す書き方が出やすい）。

### C3. 権限を絞る（必須）〔公式〕

- **規則**: `allowed-tools` は、特定のスクリプトだけに絞る（例: `Bash(python "${CLAUDE_PLUGIN_ROOT}/scripts/build.py" *)`）。`Bash(node *)` のような広い許可は書かない。agent の `tools` は、必要なものだけにする。MCP を呼ぶ agent は、`mcp__<server>__*` の形でサーバー単位に絞る。使う MCP を利用者が決める（D1）ために名前を書けない agent は、`tools` を省略してよい（省略する理由を agent の本文か README に書く）。
- **理由**: 利用者が承認する範囲を、スキルが実際に使うものにそろえるため。
- `allowed-tools` は「承認なしで実行できる許可」で、他のツールの使用を禁止するものではない（公式）。`tools` を省略すると、利用できるすべてのツールを継承する。
- プラグインの agent では、`hooks`・`mcpServers`・`permissionMode`・`initialPrompt` は無視される（公式）。

### C4. 細則は references に置く（推奨）

- **規則**: SKILL.md が長い（目安 200 行超）ときは、番号付きの手順を SKILL.md に残し、細かい規則を `references/*.md` に置いて、SKILL.md から「書く前に読む」と指示する。他のスキルは `${CLAUDE_PLUGIN_ROOT}/skills/<名前>/SKILL.md` で参照する。agent の本文は対象外とする。
- **理由**: SKILL.md を短く保ち、必要なときに必要な細則だけを読ませるため。agent の本文は毎回すべて読まれるので、分けても効果が薄い。

### C5. 副作用のあるスキルは自動で起動させない（必須）〔公式〕

- **規則**: 外部への送信、不可逆な書き込み、常駐をするスキルは、`disable-model-invocation: true` にする。それ以外の副作用のあるスキルは、同じにすることを推奨する。
- **理由**: 利用者が明示して呼んだときだけ、送信・書き込み・常駐が起きるようにするため（CLAUDE.md の「確認の基準」と合わせる）。

### C6. スキルは薄い入口にして、重い処理は委譲する（推奨）

- **規則**: 処理が長い（複数ステップで、途中の出力が多い）スキルは入口にして、サブエージェントに委譲し、`$ARGUMENTS` を渡す。引数が空のときは聞き返す。聞き方は CLAUDE.md の原則1（解釈が複数あるときは、推奨案を添えた選択肢を示す）に従う。`$ARGUMENTS` を Bash のコマンドに渡すときは、クォートし、コマンド文字列に直接つなげない。
- **理由**: 本体の文脈を守れる。
- 手順をスキルが直接持つ設計もある。その場合は、この規則を外してよい。

## D. 外部依存（MCP・ブラウザ・ライブラリ）

### D1. MCP は同梱しない（必須）

- **規則**: MCP は同梱しない（`.mcp.json`、plugin.json の `mcpServers`、marketplace.json の plugin entry の `mcpServers` を置かない。`.mcpb` ファイルも同じ）。利用者が用意したものを使う。必要なら、使う MCP の指定だけを `${CLAUDE_PLUGIN_DATA}` に保存する（プロジェクトのデータには入れない。実装例: pj-lens の `/pj-lens:mcp`）。指定がない、または MCP が使えないときは、代替手段か案内を出して止まる。推測でツールを探して使わない。
- **理由**: 同梱の MCP は、利用者の権限と通信先を、承認なしに増やす。公式は同梱を認めているが、この規則では禁止する。

### D2. 他者のルール・コードを取り込むときは出典を書く（必須）

- **規則**: 他者の文書・コードを要約・翻案して取り込むときは、出典とライセンスを、README の「出典」節か `NOTICE` に書く。`NOTICE` は、配布物に同梱されるよう、プラグイン本体（`plugins/<名前>/NOTICE`。直下がプラグインなら直下）に置く。リポジトリ直下だけに置くと、キャッシュにコピーされない（E3）。
- **理由**: ライセンスの要件を満たすため。置き場を決めておくと、レビューで確認できる。

## E. 配布メタ

### E1. plugin.json（必須）〔公式〕

- **規則**: `.claude-plugin/plugin.json` には、`name`・`version`・`description`・`author.name` を書く（公式の必須は `name` だけ。残りは社内基準で、`claude plugin validate` も警告する）。version はメタとコード（`package.json`・`__version__` など）で一致させ、更新を届けるときに上げる。agents・skills などのコンポーネントを `.claude-plugin/` の中に置かない（置いても読み込まれない）。
- **理由**: version を書くと、変えるまで利用者は同じ版に固定される。上げないと更新が届かない。メタとコードがずれると、利用者に見える版と実際の版が食い違う。

### E2. 推奨の項目（推奨）

- **規則**: `license`・`repository`・`keywords` を書く。
- **理由**: 公開・共有のとき、利用条件と出典が分かる。

### E3. リポジトリの構成（推奨）

- **規則**: リポジトリは二重構造（`plugins/<名前>/` がプラグイン本体、marketplace.json の `source` が `./plugins/<名前>`）を既定とする。tests・docs・見本はプラグイン本体の外（リポジトリ直下）に置く。リポジトリ直下をプラグインにするのは、tests・docs・見本がなく、配布物に開発物が入っても困らない極小のものだけにし、その理由を README に残す（`source` は、公式が明記している `"."` にする）。
- 参考（公式の事実）: 公式は、`plugins/<名前>/` に置き `source` を `"./plugins/<名前>"` と書く例を示している（既定や推奨とは書いていない）。相対パスの `source` は、marketplace のルート（`.claude-plugin/` を含むディレクトリ）から書く。`..` を含むと `claude plugin validate` がエラーにする。`./` で始まる必要があり、`"."` だけの `source` は「ルート自身」を指す（marketplace-reference に明記）。`"./"` は `./` で始まるので通ると読めるが、明記はない。二重構造を既定にするのは社内基準である。
- README は、リポジトリ直下に 1 つだけ置く。二重構造でも `plugins/<名前>/README.md` は作らない。marketplace の追加手順と利用者向けの詳細（H1・H4・A8・D2・H3・B2）は直下の README に書く。開発者向けの案内（tests・docs、E5 の読み込み方）は README に書かない。プラグインが複数あるときは、直下の README の中で節を分ける。
- **理由**: 二重構造なら、開発物がインストール先のキャッシュに入らない。構成の規則（E6）も 1 種類で書ける。README を 1 つにすると、同じ情報が複数の README に分かれて食い違うことがない（readme-rules.md の 1・4）。

### E4. marketplace.json（必須）〔公式〕

- **規則**: `name`・`owner.name`・`plugins[].{name,source,description}` を書く（公式の必須は `plugins[].description` を除く。`description` は `/plugin` の表示用で、社内基準で必須にする）。
- **理由**: 利用者がプラグインを選ぶときの表示のため。

### E5. 開発時の読み込み〔公式〕

- 二重構造は `claude --plugin-dir ./plugins/<名前>` で読み込む（ルートを指しても `plugins/` 配下は読み込まれない）。`claude --plugin-dir ./plugins` のように、プラグインを束ねたフォルダを渡すと、`.claude-plugin/plugin.json` を持つ直下のサブフォルダがそれぞれ読み込まれる（v2.1.265 以降）。直下がプラグインのもの（E3 の例外）は `claude --plugin-dir .`。置き場が `<名前>-inline` になる点は A2。
- 開発記録（`docs/`・`grill-specs/`）を追跡するか、gitignore するかは、この文書では決めない（実績が割れている: pj-lens は両方 gitignore、pptx-deck は `docs/specs/` だけ gitignore）。各プラグインで決め、CLAUDE.md に書く。

### E6. プラグイン本体の標準配置（推奨）

- **規則**: プラグイン本体（`plugins/<名前>/`）は、次の配置を標準とする。

      plugins/<PLUGIN>/
        .claude-plugin/plugin.json
        skills/<SKILL>/SKILL.md
        agents/<名前>.md               （agent があるときだけ）
        <入口スクリプト>               （A6。Python は python-venv.md の 2-4）
        <依存の固定用のファイル>       （A4。Python は python-venv.md の 2-2、Node は package-lock.json）
        NOTICE                         （D2。取り込んだものがあるときだけ）
        <コード・資源の置き場>         （下記）

  - **コード・資源の置き場**: 本体のコード（`scripts/`、Python のパッケージ名のディレクトリ、`tools/`・`src/` など）と、資源（`assets/`、`references/`、`data/` など）の名前は、プラグインごとに決めてよい。決めたものを README に書く。
  - **`references/`**: 1 つのスキルだけが使う細則は `skills/<SKILL>/references/` に、複数のスキルが共有する細則はプラグインのルート直下の `references/` に置いてよい（C4）。
  - tests・docs・見本は、本体の外（リポジトリ直下）に置く（E3）。この配置から外すときは、理由を README に書く。
- 参考（公式の事実）: `skills/`・`agents/`・`hooks/hooks.json`・`bin/`・`settings.json` は、プラグインのルートに置く既定の場所（公式の components ページ）。`.claude-plugin/` に置くのは `plugin.json` だけ。`scripts/` は公式でも慣例とされ、Claude Code が探すものではない。入口スクリプト・依存の固定用のファイルの位置は公式の規定がなく、この文書の規約である。pptx-deck（`pptx_deck/`・`references/`・`assets/`）と pj-lens（`tools/`・`src/`・`assets/`・`data/`）の実際の構成に合わせて、コード・資源の名前は固定しない。
- 公式の既定の場所に従い、スキル・agent・hook に独自の置き場を作らない。hooks や `bin/` を使うときは、ルート直下の公式の場所に置く（この表には、使うものだけを足す）。
- **理由**: 置き場がそろうと、C2 のパスの基準と F1 の機械検査（`${CLAUDE_PLUGIN_ROOT}/…` の実在、配布ファイルの git 管理）を、プラグイン間で同じ書き方にできる。
- この規則は本体の中の並びだけを決める。開発物が本体に入らないようにするのは E3 の役目。

## F. 検査

テストの言語は、プラグインに合わせる（Python は pytest、Node は `node:test` など）。Python のテスト全般の規則は `~\.claude\rules\python-testing.md` に従う。ここには重ねて書かない。

### F1. 最低限の検査（必須）

次の内容をテストにする。

1. 全 SKILL.md の frontmatter があり、`name` がディレクトリ名と一致する。
2. プラグイン内の SKILL.md に、ハードコードしたパス（`C:/Users` など）・`${CLAUDE_SKILL_DIR}` を書いていない。
3. SKILL.md が書く `${CLAUDE_PLUGIN_ROOT}/…` が指すファイルが実在する。
4. 相対リンク・地の文の相対パスを書いていない。
5. MCP を同梱していない（`.mcp.json` がなく、plugin.json と marketplace.json の plugin entry に `mcpServers` がない）。
6. version が、メタとコードで一致している。
7. 配布に必要なファイル（plugin.json・SKILL.md・agents・スクリプト・依存の固定用のファイル）が git 管理下にある。
8. `claude plugin validate <dir> --strict` が通る。

- 単体スキルには、1・2・4 を適用する（3 は `${CLAUDE_SKILL_DIR}/…` の実在を確かめる）。5〜8 はプラグインの規則なので適用しない。
- **理由**: 文書の規則は、機械で検査しないと、更新のたびに崩れる。
- 機械で検査しにくい規則（A5 の承認の流れ、C1 の description の内容、C3 の絞り込みの妥当性）は、G のチェックリストでレビュー時に確認する。

### F2. 追加の検査（推奨）

- SKILL.md に書いたコマンド（`<入口スクリプト> <サブコマンド>` など）が、実際にあるコマンドか。
- 待機や再試行に上限があるスキルは、上限と、超えたときの動きが書かれているか。
- 廃止したものが残っていないか（README の変更履歴と合わせて検査する。実例: pj-lens）。
- 入口スクリプトの動作: 環境がないときに終了コード 3 で止まるか、置き場がないときに終了コード 2 か。

## H. その他の規則

### H1. 対応 OS を明記する（必須）

- **規則**: Windows 専用のときは、README と plugin.json の `description` に書く。
- **理由**: A8・A9 が Windows のパスを前提にしており、他の OS では動かないため。

### H2. 名前（必須）〔公式〕

- **規則**: プラグイン名は `claude-`・`anthropic-`・`anthropics-`・`cc-plugin-` で始めず、`claude`・`anthropic`・`claude-code` などそのものも使わず、`official-claude-tools` のように `official` を `claude`・`anthropic` の隣に置かない（kebab-case にする）。marketplace 名に `inline`・`builtin`・`skills-dir`・`synced`・`npm`・`pip`・`uv`・`cargo`・`github`・`gh` などの予約語を使わない（`claudeai-` で始まる名前も不可）。
- **理由**: `claude plugin validate` がエラーにするため。

### H3. バージョンと状態の移行（推奨）

- **規則**: version は semver で付ける。`${CLAUDE_PLUGIN_DATA}` に置く設定ファイルには `schema_version` を入れ、形式を変える版では移行手順を README に書く。
- **理由**: 更新後も、置き場の既存の状態が読めるようにするため。

### H4. アンインストールの扱い（推奨）

- **規則**: アンインストールで消えるもの（`${CLAUDE_PLUGIN_DATA}`）と残るもの（A8 の共有バイナリ、利用者の成果物）を README に書く。
- **理由**: 利用者が、残るものを手で片づけられるようにするため。

### H5. 依存の取得元とパス（推奨）

- **規則**: 依存は公式のレジストリ（PyPI・npm）から取得し、可能ならハッシュも固定する（Python は `python-venv.md` の 2-6）。パスの空白・日本語（`C:\Users\<日本語名>`）を含む環境でも動くよう、コマンドのパスをクォートし、テストで確かめる。
- **理由**: 供給元の改ざんを防ぎ、Windows の実環境で壊れないようにするため。
