# 文章の書き方の規則

ユーザーに渡す文章・文書の規則。書く前に読む。

対象は、回答、説明文書、報告、提案、コミットメッセージ、ほかの文書。README は、章構成・載せる内容・表の書式を `readme-rules.md`（`~/.claude/rules/`）に従う。文・言葉・図の作り方（§3 の「図の作り方」、§4〜§7）は、このファイルに従う。§1 の書き分けの表と§2 の6段階は、README に適用しない。

## 1. 書く前に決める
説明文書以上の文書（下の表）は、読み手をその文書を初めて見る人だと想定する。書き手と同じ経緯・用語・画面を知らない人が、その文書だけを読んで、全体と次の行動を把握できるように書く。

書き始める前に、次の4つを決める。一言の返答では省略してよい。読み手が分からないときは、初見の人とする。目的・結論が決まらないときだけ、書かずにユーザーに聞く。
- 読み手: 誰が読むか。その人が前提として知っていること・知らないこと。
- 目的: 読んだあと、読み手に何をしてほしいか（実行・選択・確認・理解のどれか）。
- 結論: 1文で言い切れる主張。1文にできないなら、まだ考えが足りない。
- ストーリー: 結論に至る流れ。「なぜ今これを読むのか」から「何をしてほしいか」まで、1本につなげる。

### 書き分けの基準
文書の大きさと用途で、書く量と型を変える。迷ったら、1段上の型にする。

| 種類 | 例 | 型 | 図・表 |
|---|---|---|---|
| 一言の返答 | 質問への短い答え、確認 | 結論1〜2文。ストーリーの6段階は使わない | 不要 |
| 短い説明 | 回答、コミットメッセージ、PR 本文 | 結論 → 理由 → 行動。3〜10行 | 比較・一覧があれば表 |
| 説明文書 | 手順書、設計の説明、調査結果 | 結論 → 背景 → 課題 → 解決策 → 行動。見出しで区切る | 構成・流れがあれば図、比較する内容があれば表を入れる |
| 提案・報告 | 稟議、提案書、報告書、方針の変更案 | ストーリーの6段階をすべて使う | 全体図を1枚、比較表を1つ（比較する案がなければ省く） |

- 初見の人が読む文書（説明文書、提案・報告）は、用語の説明、背景、全体図を省かない。
- 書き手とやり取り中の短い返答は、すでに共有した内容を繰り返さない。ただし、数・名前は省かない。

## 2. ストーリーの組み立て
読み手が、途中で「なぜその話が出てくるのか」と迷わないように書く。

- 結論を先頭に書き、そのあとにストーリーを書く。
- ストーリーは、次の流れを基本にする。

| 順 | 問い | 書くこと |
|---|---|---|
| 1 | 結論 | 何を言いたいか、何をしてほしいか（1〜2文） |
| 2 | 背景 | なぜ今この話をするのか |
| 3 | 課題 | 何が問題か（数字で。数字がなければ、ないと書く。推測なら「推測」と付ける） |
| 4 | 解決策 | どうするか。選択肢があれば比較して、推奨を示す |
| 5 | 効果・リスク | 実行するとどうなるか |
| 6 | 行動 | 読み手が次にすること。誰が・何を・いつまでに。承認や選択を求めるなら、決めてほしいことと選択肢も書く。期限が不明なら「期限未定」と書く |

- 読み手に行動が必要な文書は、行動を最後に1行で書く。
- 各段落・各節の冒頭の1文に、前の内容とのつながりと、その段落の要点をまとめる（「この課題を解決するために、2案を比べた」）。
- 節の見出しだけを順に読んで、ストーリーが分かるようにする。
- 理由は、重複も漏れもないようにまとめる。並べる数は4つまでにする。
- 例外: 悪い知らせや、結論を受け止める前提が要る相手には、背景を1〜2文だけ先に置いてよい。

## 3. 図・表を使う
図・表にできる内容は、文章だけで書かず、図・表にする（§1 の表で図・表を不要とした種類を除く）。文章は、図・表の読み方と結論を書く。

| 伝えたい内容 | 使うもの |
|---|---|
| 2つ以上の比較（案、前後、製品） | 表 |
| 項目ごとの属性・設定値・一覧 | 表 |
| 手順、時間の順序 | 番号リスト。分岐があれば流れ図 |
| 全体像（文書の最初に置く） | 全体図 |
| システムの構成、モノ・人のつながり | 構成図 |
| 処理や情報の流れ | 流れ図、シーケンス図 |
| 画面の配置や操作 | 画面図、注釈つきスクリーンショット |
| 数の推移・割合 | グラフ |
| 並列の項目（順序なし） | 箇条書き |

- 図・表の前後に、その図・表で何が分かるかを1文で書く。
- 図・表には、題をつける。表は、列の見出しと単位を書く。
- 1つの図・表に、伝えることを1つだけ入れる。大きくなるなら分ける。
- 図・表の中の言葉は、本文と同じ言葉にする。

### 図の作り方
- 図は SVG で描く。配置・色・矢印・注釈を自由に決めて、初見の人が見て分かる形にする。単純な流れ図だけは Mermaid でもよい。
- SVG は別ファイルに保存し、文書から画像として参照する。保存先は、ユーザーの指定があればそこ、なければ作業フォルダの `images/`。ユーザーに渡すときは、絶対パスで書く（`environment.md` に従う）。
- 画像に代わる説明（代替テキスト）を必ずつける。
- 図に入れる文字は、本文と同じ言葉にする。文字は、表示幅 800px で 12px 以上にする。
- 色だけで区別しない。形・線の種類・文字でも区別する。
- 矢印には、何が流れるかを書く。凡例が要る図は、凡例をつける。
- SVG に、script と外部 URL の読み込みを入れない。
- 描いたら、PNG に変換して Read で表示し、文字のはみ出し・重なり・矢印の向きを確認する。変換できないときは、「未確認」と書く。
- docx・pptx など Markdown 以外の文書には、SVG を PNG に変換して貼る。
- SVG を置けない場面（コミットメッセージ・PR 本文）では、表か箇条書きに置き換える。

## 4. 段落と見出し
- 1段落に話題を1つだけ書く。段落の1文目で、その段落の要点を言う。
- 見出しは、内容が分かる言葉にする（「概要」ではなく「A案を推奨する理由」）。
- 箇条書きの項目は、文の形を揃える。

## 5. 文
- 1つの文に内容を1つだけ書く。1文は60字前後までにする。超えるなら分ける。
- 主語・対象を省かない。「これ」「それ」「上記」は使わず、名前で書く。
- 主語と述語を近くに置く。修飾語は、修飾される言葉の直前に置く。
- 能動で書く。誰が何をするかを、書き手が決めて書く。
- 否定の二重（「〜しないわけではない」）と、漢字だらけの名詞連続を避ける。

## 6. 言葉
- 「適切に」「など」「いろいろ」「なるべく」「早めに」は使わず、数・条件・名前・日付で書く。
- 同じものは、同じ言葉で書く。言い換えない。初めて出すときに、意味を書く。
- 専門用語・略語は、読み手が知らないなら、初出で説明する。
- 常体（〜する）か敬体（〜です・ます）のどちらかに統一する。既存の文書があれば、それに合わせる。
- 飾りの言葉（「〜と思われます」「〜させていただきます」）を重ねない。事実と意見を区別して書く。

## 7. 数字と出典
- 数・名前・手順は、書く前にコードや出典と照合する。照合できないものは「未検証」と書く。
- 数字には、単位・期間・比較対象をつける（「30%減」ではなく「処理時間が40秒から28秒に減（30%減）」）。
- 事実と、書き手の推測・判断を分ける。推測には「推測」と書く。

## 8. 渡す前の確認
- この文書を初めて見る人が、他の資料や経緯を知らなくても、全体と次の行動を把握できるか。
- 先頭の3行だけ読んで、結論と求める行動が分かるか。
- 見出しだけを順に読んで、ストーリーが分かるか。
- 図・表にできる箇所を、文章で書いていないか。
- 読み手が知らない言葉・略語が残っていないか。
- 削っても意味が変わらない文・語がないか。削る。
- 行動が必要な文書で、行動が末尾に1行で書かれているか。
- 数字・固有名詞を、出典と照合したか。
- トークン・個人情報・社内パスなど、載せてはいけない情報が、文書や図に混ざっていないか。
