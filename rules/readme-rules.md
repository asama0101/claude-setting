# README の書き方の規則

README.md を書く、または変更するときに従う規則。目的は、初めて読む利用者が、迷わず導入し、最初の成功までたどり着けることである。

- 規則には **必須** と **推奨** がある。推奨は、守らない理由があれば外してよい。必須を外すときは、利用者に理由を示して了承を得る。
- 各規則の末尾に、確認方法を〔機械〕（コマンドで確認できる）か〔目視〕（レビューで見る）で示す。
- 既存の README には、新規と変更した節から適用する。一括で書き直さない。ただし、利用者が刷新を明示して頼んだときは、全体に適用して書き直してよい。
- グローバルの CLAUDE.md の「文章の書き方」はここに重ねて書かない。そちらに従う。

## 1. 読者

### 1-1. 読者を「ツールを使う人」に固定する（必須）

- **規則**: 読者は「ツールを使う人」（自分とチーム）に固定する。開発者向けの情報（内部構造、開発環境の構築、テスト方法）と、設計判断（なぜそうしたか、何を見送ったか）は、README に書かない。
- **理由**: 使う人が、必要な情報にすぐ届くようにする。〔目視〕

### 1-2. 同じ情報を複数の文書に書かない（必須）

- **規則**: 導入方法やコマンド表の情報は、README とほかの文書の間で重複させない。1 か所に決め、ほかからはリンクにする。
- **理由**: 書き分けると、更新のたびに食い違う。〔目視〕

## 2. 章構成と先頭

### 2-1. 章は次の順番で書く（必須）

- **規則**: 次の順番で書く。順番は変えない。
  1. タイトルと 1 行説明
  2. 機能
  3. 前提条件（該当しなければ省略してよい）
  4. 導入方法
  5. 使い方
  6. 設定（該当しなければ省略してよい）
  7. 困ったとき（該当しなければ省略してよい）
  8. ライセンス（該当しなければ省略してよい）
- 上の章に収まらない項目（初回の準備、更新、アンインストール）は、最も近い章の中に小見出し（###）として置く。章を増やさない。
- **理由**: どの README でも、同じ場所に同じ情報がある。〔機械: 見出しの抽出〕

### 2-2. 先頭の 1 画面で伝える（必須）

- **規則**: タイトルと 1 行説明で、「何のツールか・誰向けか・使うと何ができるか」を書く。
- **理由**: 続きを読むかを、利用者が先頭で判断できるようにする。〔目視〕

### 2-3. 機能は効果で書く（必須）

- **規則**: 箇条書きで 3〜5 項目。見出しは「機能」とする（「できること」は使わない）。ファイル名の列挙にせず、「何が楽になるか」を書く。
- **理由**: 利用者は、仕組みではなく効果で選ぶ。〔機械: 項目数。効果で書いているかは目視〕

## 3. 書き方

### 3-1. 手順は実行して確認する（必須）

- **規則**: 導入方法と使い方のコマンドは、コピーして実行できる形（コードブロック）で書く。書いた後に、新しい環境（または一時フォルダ）で、手順どおり実行して確認する。実行できないときは「未検証」と報告に明記する。README 本文には書かない。
- **理由**: 動かない手順は、利用者が最初に離れる原因になる。〔目視: 報告〕

### 3-2. 使い方は最短の成功を見せる（必須）

- **規則**: 最も基本的な例を 1 つ載せる。ツールの目的の成果が目に見える最短の操作にし、コマンドと期待される出力を書く。ライブラリや設定集は、「コマンド」を「呼び出し例」「確認の操作」と読み替える。
- **理由**: 導入が成功したかを、利用者が自分で判断できるようにする。〔目視〕

### 3-3. 前提条件は確認できる形で書く（必須）

- **規則**: OS、必要なソフトとバージョンを書く。確認コマンドがあるものには、それを添える。
- **理由**: 手順の途中で、前提の不足に気づかないようにする。〔目視〕

### 3-4. 用語は初出で説明する（必須）

- **規則**: グローバルの CLAUDE.md の「文章の書き方」（初めて出すときに意味を書く）に従う。設定表の用語も対象にする。
- **理由**: 読者は、書き手の用語を知らないものとして書く。〔目視〕

### 3-5. 上書き・削除の前に警告し、戻せるようにする（必須）

- **規則**: 上書きや削除を伴う手順は、警告をその手順の前に置く。元に戻す方法を書く。
- **理由**: 実行した後に警告を読んでも、遅い。〔目視〕

### 3-6. 数と名前は照合する（必須）

- **規則**: グローバルの CLAUDE.md の「文章の書き方」（書く前に照合する）に従う。README では、項目の数、コマンド名、フラグが対象で、照合先はコード。
- **理由**: 古い数や名前は、利用者の誤操作につながる。〔機械: `grep` やコマンドの実行〕

### 3-7. 更新と削除の手順を書く（推奨）

- **規則**: 更新の手順と、アンインストール（元に戻す）の手順を、導入方法の小見出し（###）に書く。上書きや削除を伴うツールでは、3-5 により、元に戻す方法が必須になる。
- **理由**: 導入した後に困る利用者を減らす。〔目視〕

### 3-8. 困ったときは、画面の文言で引ける形にする（推奨）

- **規則**: エラーは、画面に出る文言をそのまま見出しにし、原因と対処を書く。
- **理由**: 利用者は、画面の文言で検索して探す。〔目視〕

### 3-9. 表と図（推奨）

- **規則**: 表のセルは 1 文にする。長い補足は、表の下に箇条書きで書く。画面の操作が 3 手順以上なら、図か画像を使う。目次は書かない（GitHub が見出しから自動で出す）。
- **理由**: 長いセルは読みにくく、手順は図のほうが速く伝わる。〔目視〕

### 3-10. リンクが開くことを確かめる（推奨）

- **規則**: 相対リンクと URL が開くことを確かめる。
- **理由**: リンク切れは、利用者の行き止まりになる。〔機械: リンクチェック〕

## 4. README を置く場所

### 4-1. README はリポジトリ直下に 1 つだけ置く（必須）

- **規則**: README は、リポジトリ直下に 1 つだけ置く。プラグインやパッケージのフォルダの中には置かない。ライセンスや出典の注記は、そのフォルダの `NOTICE` に書く。
- **理由**: GitHub は、`.github`、直下、`docs` の順に README を選ぶ。複数あると、どれが表示されるかが分かりにくい。〔機械: ファイル検索〕

## 5. チェックリスト

### 必須
- [ ] 1-1 読者はツールを使う人。開発者向けの情報と設計判断は README に書かない〔目視〕
- [ ] 1-2 同じ情報を複数の README に書いていない〔目視〕
- [ ] 2-1 章が決められた順番で、章を増やしていない〔機械〕
- [ ] 2-2 先頭の 1 画面に、何のツールか・誰向けか・使うと何ができるかがある〔目視〕
- [ ] 2-3 機能が効果で書かれ、3〜5 項目〔機械・目視〕
- [ ] 3-1 手順を実行して確認した（未検証は報告に明記）〔目視〕
- [ ] 3-2 使い方に、最短の成功と期待される出力がある〔目視〕
- [ ] 3-3 前提条件に、バージョンと確認コマンドがある〔目視〕
- [ ] 3-4 初出の用語・略語に、1 文の意味がある〔目視〕
- [ ] 3-5 上書き・削除の手順の前に警告があり、戻し方がある〔目視〕
- [ ] 3-6 数と名前を、コードと照合した〔機械〕
- [ ] 4-1 README はリポジトリ直下に 1 つだけ〔機械〕

### 推奨
- [ ] 3-7 更新と削除の手順がある〔目視〕
- [ ] 3-8 困ったときが画面の文言で引ける〔目視〕
- [ ] 3-9 表のセルは 1 文で、3 手順以上の操作に図がある〔目視〕
- [ ] 3-10 リンクが開く〔機械〕
