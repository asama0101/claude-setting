# README の書き方の規則

README.md を書く、または変更するときに従う規則。GitHub の慣習（Make a README）に従い、慣習から外れる点だけを書く。実際の README（grill-spec・html-report・pptx-maker・project-lens・vault-inbox）で共通していた形を、規則にしてある。

- 既存の README には、新規と変更した節から適用する。利用者が刷新を頼んだときだけ、全体を書き直す。
- 文章の書き方は `reference\writing.md` に従う（§1 の書き分けの表と§2 の 6 段階は、README に適用しない）。図の作り方は、`reference\writing.md` の「図の作り方」に従う。

## 1. 読者と範囲

- 読者は、ツールを使う人にする。初めて見る人が、README だけで導入と最初の 1 回の実行まで進めるように書く。
- 内部構造、開発環境、テスト方法、設計判断は、README に書かない。開発者向けの内容は `docs/development.md` に置く。
- 長さの目安は 140 行以内にする（空行を含み、画像の行は数えない。5 つの README の実測は 93〜140 行）。超えるときは、詳細を `docs/` に移して、リンクにする。
- 利用者の判断に要る範囲（何を読み、書き、消すか。安全のための作り）は書いてよい。それ以外の内部構造は書かない。
- 対象は、Claude Code プラグインなど、利用者に配るツールの README。`.pytest_cache` などの自動生成の README は対象外。
- 同じ内容は 1 か所にだけ書く。導入方法やコマンド表は README に置き、ほかの文書からはリンクにする。

## 2. 章の構成

次の順に書く。該当しない章は省く。順番は変えない。

| 順 | 章 | 書くこと |
|---|---|---|
| 1 | タイトルと 1 行説明 | 何のツールか、誰向けか。OS は、ここか導入方法の冒頭のどちらかに書く。直後に、最も基本的なコマンドを 1 つ（コードブロック）。そのあとに全体図を 1 枚（機能の先頭に置いてもよい） |
| 2 | 機能 | できることの一覧。できないことがあるなら、できること・できないことの表にする |
| 3 | 導入方法 | 冒頭に前提。次にコマンドの手順 |
| 4 | 使い方 | 流れの図と、最も基本的な例 |
| 5 | 設定 | 利用者が変えられる項目を、表で |
| 6 | 困ったとき | 症状と対処 |
| 7 | ライセンス | 種類と LICENSE へのリンク。出典の注記は NOTICE へのリンク |

- 「前提条件」の章は置かない。前提は、導入方法の冒頭に書く。
- 上の章に収まらない項目（更新、アンインストール、オフラインや clone での導入、環境の点検）は、導入方法の小見出し（###）に置く。
- 目次は書かない。GitHub が見出しから自動で出す。
- リポジトリの `tests/` や `CLAUDE.md` が章の順番を検査していることがある（grill-spec）。章を足す・並べ替えるときは、同じ作業で、テストと `CLAUDE.md` を直す。
- 文体（常体・敬体）は、既存の README に合わせる。新規は常体にする。

## 3. 章ごとの書き方

### タイトルと 1 行説明

- 1 行説明は、「〜する Claude Code プラグイン」のように、種類と目的を 1 文で言い切る。
- 最も基本的なコマンドは、そのまま貼って動く形で書く（例の引数まで書く）。

### 機能

- 機能は、箇条書きか図で示す。長い説明は書かない。
- できること・できないことは、表にする（列は「項目」「できること」「できないこと」）。

### 導入方法

- 冒頭に、OS、必要なソフトとそのバージョン、ネットワークが要るかどうかを書く。任意のものは「任意:」と分ける。動作を確かめたバージョンがあれば添える。
- 手順は、番号付きの小見出し（### 1. 〜）か、コードブロックの連続で書く。コマンドは、すべてコードブロックにする。
- 導入が終わったことを確かめる方法（コマンドや、画面に出るもの）を 1 つ書く。
- 更新とアンインストールは、あれば小見出しにして、各 1〜2 行とコマンドで書く。アンインストールでは、何が消え、何が残るかを書く。長いときは `docs/` に移す。

### 使い方

- 最初に、最も基本的な例を 1 つ載せる。コマンドと、期待される出力か画面を書く。
- 流れは、番号付きの手順か、図で見せる。分岐があるときは、図にする。
- 使い方が複数ある（毎朝の流れ、突発の登録など）ときは、場面ごとに小見出し（###）を切る。
- コマンドが複数あるときは、コマンドの表（コマンド・内容）にする。手動でしか起動しないものは、列で示す。
- 内部で使うだけのコマンドは、載せない。

### 設定

- 表（項目・内容）にする。環境変数やファイルの名前は、コードの表記どおりに書く。
- 表に入らない補足は、表の下に書く。

### 困ったとき

- 画面に出る文言（エラー、`[NG]` の行）を、そのまま見出しにする。見出しの下に、原因と対処を書く。
- 症状が 3〜4 件で、対処がそれぞれ 1 文なら、「症状」「対処」の表にしてよい。
- 件数が多いときは、README には代表的なものだけ書き、残りは `docs/troubleshooting.md` へのリンクにする。

### ライセンス

- 種類と、LICENSE へのリンクを書く。翻案や同梱物があるときは、出典と NOTICE へのリンクを 1 文で書く。

## 4. 図・表・警告

- 図は SVG にして `docs/images/` に置き、`<img src="docs/images/〜.svg" alt="〜" width="800">`（または `![alt](docs/images/〜.svg)`）で参照する。`alt` に、図が伝える内容を文で書く。図の題は付けず、`alt` で代える。画面のスクリーンショットは PNG にしてよい。並べるときは、幅を小さくしてよい（例: 3 枚で 260）。
- 図は、次のものに使う。それ以外は、表か番号付きの手順にする。
  - 全体図
  - 流れ（処理の順序や分岐）、状態の遷移
  - 画面の見方や操作
  - 成果物の構成（できあがるファイルの置き場）
- 表のセルは 1 文にする。長い補足は、表の下に書く。
- 上書き・削除・外部への送信を伴う手順は、その手順の前に警告を置く。警告には、何が起きるかと、戻し方（戻せないときは、戻せないこと）を書く。書式は、次のとおりにする。種類を区別するときは、`**上書きの警告:**` のように、「警告:」の前に語を足してよい。

  ```
  > **警告:** 〜が消え、戻せない。残したいときは、先に〜へコピーする。
  ```

- 使う前に知るべき注意が 3 件以上あるときは、1 つの引用ブロックに、箇条書きでまとめる。

  ```
  > **警告: 使う前に**
  >
  > - **原本を移す**: 〜。戻すには〜。
  > - **先にバックアップする**: 〜。
  ```

## 5. 置き場所とリンク

- README と `LICENSE` は、リポジトリ直下に 1 つだけ置く。プラグインやパッケージのフォルダには、README を置かない。出典の注記は、そのフォルダ直下の `NOTICE` に書き、README からリンクする。
- 詳細は、`docs/` に分ける。README からは、見出しのアンカー付きでリンクする（例: `docs/usage.md#設定の補足`）。

  | 内容 | 置き場所 |
  |---|---|
  | 手順の詳細、設定の補足 | `docs/usage.md`（または `docs/guide.md`） |
  | 多数のエラーの対処 | `docs/troubleshooting.md`（または `docs/guide.md` の節） |
  | 素材の扱い、安全、実機での確認など | `docs/` に、内容が分かる名前で |
  | 開発者向けの内容 | `docs/development.md` |

## 6. 書いたあとの確認

- 導入方法と使い方の手順を、新しい環境で実行する。上書き・削除の手順は、検証用の環境かコピーで実行する。実行できなかった手順は、README に「未検証」と書き、報告にも書く。
- 項目の数、コマンド名、フラグ、ファイル名は、コードと照合する。
- 利用者が見る内容を変えたら、README も同じ作業の中で直す。

## 7. チェックリスト

- [ ] 章の見出しが 2 の順番である（`grep '^## '` で確認）。テストが章順を検査するリポジトリは、テストも通った
- [ ] 140 行以内である（`wc -l` で確認）。超えるときは `docs/` へのリンクにした
- [ ] 1 行説明の直後に、基本のコマンドと全体図がある
- [ ] 導入方法の冒頭に、OS・ソフトのバージョン・ネットワークの要否がある
- [ ] 画像のファイルが実在し、`alt` がある。SVG を PNG に変換して、目で確かめた
- [ ] README がリポジトリ直下に 1 つだけある（`find` で確認）
- [ ] コマンド名・フラグ・ファイル名が、コードにある（`grep` で確認）
- [ ] 手順を実行した、または「未検証」と書いた
- [ ] 上書き・削除の手順の前に、警告と戻し方がある
- [ ] 内部構造・開発環境・テスト方法を書いていない
