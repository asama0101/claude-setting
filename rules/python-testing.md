# Python のテスト規則

Python のコードにテストを書くときに従う規則。プラグインに限らず、Python 全般に当てはまる。

- 規則には **必須** と **推奨** がある。推奨は、守らない理由があれば外してよい。必須を外すときも、利用者に理由を示して了承を得る。
- グローバルの CLAUDE.md の規則（TDD・完了前の検証）はここに重ねて書かない。そちらに従う。
- Node のテストは対象外（`node:test` を使う）。
- 各規則の末尾に、確認方法を〔機械〕（コマンドで確認できる）か〔目視〕（レビューで見る）で示す。

## 1. 道具と設定

### 1-1. テストは pytest で書き、実行する（必須）

- **規則**: テストの実行は `pytest` にする。テストは pytest の関数形式で書く。`unittest.TestCase` の既存テストは、pytest で実行はできるが、fixture 引数と `parametrize` は使えない。触るなら関数形式に書き直す。〔機械: テストファイルに `unittest.TestCase` がない〕
- **理由**: フィクスチャ・パラメータ化・`tmp_path`・`monkeypatch` が使え、実行の入口を 1 つにそろえられる。

### 1-2. 依存と設定（必須）

- **規則**:
  - テストの依存（`pytest`・`pytest-cov`）は `requirements-dev.txt` に `==` で固定する。
  - テストは、開発用の venv（`python-venv.md` の 1。プラグインでは 2 の専用 venv）に `requirements-dev.txt` を足した環境で実行する。配布する環境には入れない。開発者自身の環境なので、導入に 2-3 の承認は要らない。
  - pytest の設定は `pyproject.toml` の `[tool.pytest.ini_options]` に 1 か所だけ置く（pytest 9 以降は `[tool.pytest]` でもよい）。pytest の設定を含む `pytest.toml`・`pytest.ini`・`tox.ini`・`setup.cfg` を併存させない（先に見つかった 1 つだけが使われ、空の `pytest.ini` でも `pyproject.toml` の設定は無視される）。
  - `testpaths`・`addopts = ["--strict-markers", "-ra"]`・`xfail_strict = true` を書く。使うマーカー（`slow`）は、同じ設定の `markers` に登録する。未登録だと、`--strict-markers` で収集時にエラーになる。
- **理由**: テストの実行結果を、実行環境の版で再現するため。設定が複数あると、どれが効くかが分からなくなる。〔機械: 設定ファイルの確認〕

### 1-3. カバレッジは `pytest-cov` で測る（推奨）

- **規則**: `--cov=<対象のパッケージ> --cov-branch --cov-report=term-missing` で測り、未実行の行と分岐を探すために使う。目標値にしない。意図して実行しない行は、理由をコメントに残す。
- **理由**: カバレッジは「実行された行」しか測らない。assert のないテストでも上がるので、質の指標にならない。

### 1-4. 重要なロジックは変異テストで確かめる（推奨）

- **規則**: 判定・計算・変換の中心になる関数は、`mutmut` で、コードを壊してもテストが落ちることを確かめる。実行頻度は、リリース前か、その関数を変更したときに限る。`mutmut` は Windows では WSL 内でしか動かない（公式 README）ので、WSL を使えないときは、手で実装の分岐を壊してテストが落ちることを確かめる。
- **理由**: 見せかけのテストを機械で見つける代表的な方法のため。

## 2. 見せかけのテストをしない（必須）

次のテストは書かない。この列挙に当てはまらなくても、「実装を壊しても落ちない」テストは見せかけとみなす。

- **2-1. assert のないテスト**: 例外が出ないことだけを見る場合は、そのことをテスト名に書く。〔目視〕
- **2-2. モックだけを確かめるテスト**:
  - 禁止: 仕込んだ戻り値の再確認、呼ばれたかどうかだけの確認。
  - 可: 境界への送信内容（引数・回数）の確認。ただし、その結果として対象が返す値か状態も 1 つ以上確かめる。〔目視〕
- **2-3. 実装を写したテスト**: 期待値は、テスト対象のコードを呼ばずに、リテラルまたは仕様から導いた別の手段で決める。`parametrize` の期待値を式で組み立てない。プロパティベーステスト（`hypothesis`）は、この限りでない。〔目視〕
- **2-4. 常に通るテスト、弱い assert だけのテスト**:
  - `assert True`、条件が常に真の assert、`try/except` で失敗を握りつぶす。
  - `is not None`・型の確認・`len(x) >= 0` だけで終わるもの。期待する具体値を確かめる。
  - 広い `pytest.raises(Exception)`。具体的な例外型と `match` を付ける。
  - `if` の中の assert（条件が偽なら実行されない）。〔機械: `ruff` の `PT011`・`B017`（広い `pytest.raises`）。他は目視〕
- **2-5. 往復だけ・正常系だけのテスト**: `decode(encode(x)) == x` だけで仕様を見ないもの。異常系や境界値を持つ関数の、正常系だけのもの。〔目視〕
- **2-6. 環境や他のテストに依存して偶然通るテスト**: 実行順、既存のファイル、現在時刻、他のテストが作ったデータに依存する。独立性は 3-3。
- **2-7. 理由のないスキップと放置された xfail**:
  - `skip`・`skipif`・`xfail` には `reason=` を付ける。`xfail` には、Issue 番号か期限も付ける。`xfail` は `strict=True`（設定の `xfail_strict` でそろえる）。
  - `skipif` は環境要因のみ。〔機械: `pytest -ra` の出力で、SKIPPED・XFAIL の理由を一覧して確認〕
- **2-8. 失敗を確認していないテスト**: 新しいテストは、実装を入れる前（または分岐を壊して）に落ちることを一度見る。その赤の出力を、4 節の報告に添える。〔目視: 報告の赤の出力〕

- **理由**: 通っているのに何も守っていないテストは、壊れていることに気づく機会を奪い、「テストが通った」という報告の根拠を無効にする。

## 3. 書き方

### 3-1. 外部だけを置き換える（必須）

- **規則**: 置き換えてよいのは、テスト対象の外にあるものだけ。具体的には、ネットワーク、時刻、乱数、環境変数、利用者の入力、他のツールの実行（外部コマンド）。自分のコードの内部（自分の関数・クラス・モジュール）は置き換えない。
- 機能（利用者が呼ぶ入口: CLI コマンド・公開関数・スキル）ごとに、置き換えを使わない統合テストを最低 1 本持つ。入口スクリプトのように自分のコードを起動する `subprocess` は、実際に起動する。外部はテスト用の代替（`tmp_path`・ローカルのサーバー）でよい。
- **理由**: 内部まで置き換えると、実装を写したテスト（2-3）になり、リファクタリングのたびに壊れる。〔目視: 機能の一覧と統合テストの対応〕

### 3-2. 一時ファイルは `tmp_path` を使う（必須）

- **規則**: テストが作るファイルは、`tmp_path` フィクスチャで作る。プロジェクト内や固定のパスに作らない。パスの空白・日本語を確かめるテストでは、`tmp_path` の下に空白や日本語を含むサブディレクトリを作って使う。
- **理由**: テスト同士が干渉せず、リポジトリを汚さない。一時フォルダには、直近 3 回の実行分が残る（`tmp_path_retention_count`）。`--basetemp` を指定すると毎回消える。〔機械: `grep` で `tempfile`・固定パスを探す〕

### 3-3. テストは独立させる（必須）

- **規則**: テストは単独でも、任意の順でも通る。他のテストの副作用（グローバル状態、環境変数、カレントディレクトリ、モジュール変数）に依存しない。環境変数やカレントディレクトリは `monkeypatch` で変える。結果が実行のたびに変わるテスト（フレーキー）を、再実行で通して済ませない。原因を直す。
- **理由**: 順序や再実行に頼ったテストは、変更の影響を正しく示さない。〔機械: `pytest path::test_name` の単独実行で通る。`pytest-randomly` を入れると、順序を変えても通ることを確かめられる（任意）〕

### 3-4. バグの修正には再現テストを付ける（必須）

- **規則**: バグを直すときは、そのバグで落ちるテストを先に書き、赤の出力を残してから直し、通す。
- **理由**: 同じバグの再発を防ぎ、直ったことの根拠になる。〔目視: 報告の赤の出力〕

### 3-5. 時刻・乱数・待機・非同期（推奨）

- **規則**: 時刻は `monkeypatch` か `time-machine` で固定する。乱数は seed を固定するか、注入する。`sleep` で待たず、条件を待つ。非同期は `pytest-asyncio` を使い、テスト内で `asyncio.run` を直接呼ばない。
- **理由**: 実行のたびに結果が変わるのを防ぐ。

### 3-6. フィクスチャ（推奨）

- **規則**: 共有するフィクスチャは `conftest.py` に置く。`session`・`module` スコープのフィクスチャは、テストが変更しない値だけにする。テスト対象の振る舞いを確かめる assert を、フィクスチャの中に置かない（前提の確認はよい）。後始末は `yield` の後に書く。
- **理由**: 状態の共有が、独立性（3-3）を壊すのを防ぐ。

### 3-7. 配置・命名・パラメータ化（推奨）

- **規則**: テストは `tests/` に `test_*.py` として置く（pytest は `*_test.py` も探すが、名前は `test_*.py` にそろえる）。ソースは `src/` に置き、`pip install -e .` でテストする。既定の import モード（`prepend`）では、同名のテストファイルが衝突するので、`tests/` の下のファイル名を一意にするか、`--import-mode=importlib` を使う。テスト名に、条件と期待する結果を書く（例: `test_環境がないとき終了コード3で止まる`）。入力違いは `pytest.mark.parametrize` で書き、`ids=` を付ける。遅いテストは `@pytest.mark.slow` を付け、`--durations=10` で確認する。
- **理由**: 失敗したときに、何が壊れたかがテスト名から分かる。

### 3-8. 検証と置き換えの道具を使い分ける（推奨）

- **規則**: 例外は `pytest.raises(E, match=re.escape("…"))` で確かめる（`match` は正規表現として検索されるので、記号を含む文言は `re.escape` する）。標準出力は `capsys`、ログは `caplog` で確かめる。環境変数・属性は `monkeypatch` で変える。呼び出しの確認に `unittest.mock` を使うときは、`autospec=True` を付ける。
- **理由**: 道具をそろえ、実装の詳細に依存しない形にする。〔目視〕

## 4. 報告

- **規則**: 「テストが通った」と報告するときは、`pytest -ra` の実行出力（件数・失敗・スキップと理由）を根拠として示す。新しいテストは、2-8 の赤の出力も添える。
- **理由**: 完了前の検証（CLAUDE.md）の根拠を、テストの出力に置くため。
- Windows で日本語のテスト名が文字化けするときは、`PYTHONUTF8=1` を付けて実行する。
